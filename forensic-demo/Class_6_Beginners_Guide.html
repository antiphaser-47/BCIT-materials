1. 這堂課到底在教什麼？

想像一下這個情境：

  • 有一間貨運公司 HarbourLine Logistics Ltd 被調查。
  • 警方扣押了他們的電腦。
  • 但在扣押前一天，有人把一些重要的 貨運艙單（shipping manifest） 刪掉了。
  • 檢察官問你：「檔案還能找回來嗎？裡面寫的收貨人是誰？」

這堂課就是在教你：用算術和邏輯，把已經被「刪除」的檔案從磁碟中完整挖出來，而且證明它沒有被篡改過。

2. 先建立基本觀念——刪除檔案時，電腦到底做了什麼

大部分初學者會以為「刪除 = 檔案不見了 = 資料被清掉了」。但真相是：

刪除只做了一件事：把檔名標記為「可重用」。

更精確地說，電腦只動了 一個 byte：

範例：檔案 NOTES.TXT

刪除前：  4E 4F 54 45 53 20  54 58 54 00 00 00  48 65 79 20 4A 61
          N  O  T  E  S  ·   T  X  T           H  e  y     J  a

刪除後：  E5 4F 54 45 53 20  54 58 54 00 00 00  48 65 79 20 4A 61
          ·  O  T  E  S  ·   T  X  T           H  e  y     J  a

只有第一個 byte 從 4E 變成 E5，其他全部原封不動。

在 FAT 檔案系統中，E5 是「已刪除」的標記。而在 NTFS 中，則是改變 MFT 記錄裡的一個欄位（我們之後會看到）。

所以「刪除」的真正意義是：系統告訴未來要寫入的檔案「這個位置可以用了」，但原始的資料還躺在那裡，直到被新檔案蓋過去為止。

3. 兩種找回檔案的方法

方法一：走地圖方法二：雕刻（Carving）
如果檔案系統的「地圖」（MFT 記錄）還在，就照著地圖走。 如果地圖已經消失，就在整顆硬碟上搜尋「看起來像檔案」的簽名。
優點：得到完全正確的檔案——正確的區塊、正確的順序、正確的長度。 優點：即使檔案系統整個壞掉也能用。
缺點：地圖不見就沒輒。 缺點：無法處理碎片，且沒有檔名、時間等 metadata。
本課程的策略：先嘗試方法一（今天的主軸），真的不行再用方法二。

4. 磁碟的基本單位：Sector、Cluster、LCN、VCN

要讀懂後面的內容，你必須先熟悉以下四個名詞。我們用一個圖書館的比喻來說明：

名詞定義圖書館比喻這裡的數值
Sector（磁區） 硬碟最小的讀寫單位 一本書 512 bytes
Cluster（叢集） 檔案系統一次分配的最小空間 一個書架（放了好幾本書） 8 個 sectors = 4,096 bytes
LCN
Logical Cluster Number		 這個叢集在「整顆磁碟」上是第幾個 書架的「棟+層+架」編號（絕對位置） 從 0 開始數到最大叢集數
VCN
Virtual Cluster Number		 這個叢集在「這個檔案裡面」是第幾個 一本書的「頁碼」 從 0 開始數到檔案結束

最重要的公式——牢記它

Cluster Size = Bytes per Sector × Sectors per Cluster
             = 512 × 8
             = 4,096 bytes

Byte Offset = LCN × Cluster Size
            = LCN × 4,096

什麼是 byte offset？ 就是檔案裡的某個資料在整顆磁碟的哪個位置（第幾個 byte）。當我們要用十六進位編輯器（如 HxD、X-Ways）跳到某個位置時，就是輸入這個數字。

5. $Boot——磁碟的身分證（怎麼量測磁碟）

每一顆 NTFS 磁碟的第一筆資料叫做 $Boot。它就像磁碟的身分證，記錄了磁碟的所有基本資訊。

為什麼要先讀 $Boot？因為如果你不知道 Cluster 有多大、$MFT 從哪裡開始，後面什麼都做不了。
欄位偏移位置大小說明
Bytes per Sector 0x0B 2 bytes（Little Endian） 例如 00 02 反轉為 0x0200 = 512
Sectors per Cluster 0x0D 1 byte 例如 08 = 8
$MFT 起始叢集 0x30 8 bytes（Little Endian） 告訴你 MFT 這張表格從哪個叢集開始

一步步實作：怎麼讀 $Boot

  1. 打開磁碟映像檔的第一個 sector（前 512 bytes）
  2. 跳到 offset 0x0B，讀取 2 bytes → 反轉 → 得到 bytes per sector
  3. 跳到 offset 0x0D，讀取 1 byte → 得到 sectors per cluster
  4. 兩者相乘 = cluster size
  5. 跳到 offset 0x30，讀取 8 bytes → 反轉 → 得到 $MFT 的起始 LCN
  6. 將 LCN × cluster size = $MFT 的 byte offset
  7. 跳到那個 offset——你應該會看到 FILE0 簽名

6. MFT——檔案的戶口名簿

MFT 是什麼？

MFT（Master File Table，主檔案表）是 NTFS 最核心的資料結構。你可以把它想像成一個 戶口名簿，每一個檔案或目錄 都在這本名簿裡有一筆記錄。

即使在這個課程中，我們要復原的是「已刪除」的檔案，它的 MFT 記錄仍然可能還存在——這就是我們能復原它的關鍵。

MFT 的結構

  • 每筆記錄固定 1,024 bytes
  • 第一筆記錄（record 0）是 $MFT 自己
  • 第二筆（record 1）是 $MFTMirr（MFT 的備份）
  • 後續還有 $LogFile、$Volume、$AttrDef 等系統檔案
  • 真正的使用者檔案從記錄編號較高的位置開始

計算任一記錄的 byte offset

Record n 的起始位置 = $MFT 偏移 + (n × 1,024)

範例：如果 $MFT 在 byte 49,152，要找 record 61：
49,152 + (61 × 1,024) = 49,152 + 62,464 = 111,616

記錄簽名：FILE0

每筆 MFT 記錄的前 4 個 bytes 一定是 46 49 4C 45（ASCII 的 FILE），第 5 個 byte 是 30（0）。

所以如果你在十六進位編輯器中搜尋 ASCII 字串 FILE0，你會找到磁碟上所有的 MFT 記錄——包括來自已不存在之磁碟的殘留記錄。

搜尋 FILE0 而不只是 FILE，能減少誤判。因為 0（30）是下一個欄位的一部分，不是檔案名稱的一部分。

7. Allocation Status——怎麼一眼看出「這是刪除的檔案」

在每筆 MFT 記錄的標頭中，有一個非常重要的 2-byte 欄位：

記錄內偏移大小意義
0x162 bytesAllocation Status（配置狀態）

這個欄位的值代表：

數值意義
00 00已刪除的檔案
01 00正常分配的檔案
02 00已刪除的目錄
03 00正常分配的目錄
這就是全部了。 檔案和已刪除檔案之間的差別，僅僅是 MFT 記錄中 offset 0x16 的兩個 bytes。資料本身完全沒有被碰過。

所以在實務上，要找到已刪除的檔案，你只需要：

  1. 跳到你懷疑的 MFT 記錄
  2. 跳到記錄內 offset 0x16
  3. 讀取 2 bytes，看是不是 00 00 或 02 00

8. MFT 記錄內部的屬性標籤

一個 MFT 記錄（1,024 bytes）就像一個箱子，裡面有多個「屬性（Attribute）區塊」，每個區塊開頭都有一個標籤告訴你「我是誰」：

屬性 ID名稱內容
0x10$STANDARD_INFORMATION時間戳記（建立、修改、存取、刪除時間）
0x30$FILE_NAME檔名
0x80$DATA檔案內容本身，或指向內容的地圖（Runlist）
FF FF FF FF記錄結束標記
在十六進位編輯器中搜尋 80 00 00 00（$DATA 的簽名）就可以找到檔案的內容或地圖。

Resident vs Non-Resident

在 $DATA 屬性的第二個 byte，有一個關鍵的旗標：

  • 00 = RESIDENT（常駐）：檔案非常小（約 600 bytes 以下），內容直接存在 MFT 記錄裡面。你可以在記錄中直接讀出檔案內容。
  • 01 = NON-RESIDENT（非常駐）：檔案比較大，內容散落在磁碟各處。MFT 記錄內存放的是 Runlist——一份告訴你「去哪裡找檔案碎片」的地圖。
本課程的目標：我們要復原的檔案是 NON-RESIDENT 的，所以關鍵在於讀懂那份 Runlist。

9. $DATA 屬性與 Runlist——檔案的「地圖」

當一個檔案是 NON-RESIDENT 時，它的 $DATA 屬性裡放的是一串編碼過的數字，這些數字描述：這個檔案的內容分散在磁碟上的哪些叢集中。

我們用下面的例子來說明：

檔案 manifest_0448.png 的實際情況

這個檔案總共佔用 58 個叢集，但因為磁碟空間不連續，它被拆成 3 段 儲存：

Run 1: 起始 LCN = 12,592, 長度 = 24 叢集  (VCN 0-23)
Run 2: 起始 LCN =  7,592, 長度 = 20 叢集  (VCN 24-43)
Run 3: 起始 LCN = 16,592, 長度 = 14 叢集  (VCN 44-57)

注意：Run 2 在磁碟上的位置（LCN 7,592）在 Run 1（LCN 12,592）之前！這叫碎片化（fragmentation）。

檔案在磁碟上是散亂儲存的，但我們要按照 VCN 順序（0→1→2→…→57）把它們重新拼起來。

Runlist 就是這樣一份清單，記錄了每一段（Run）的：

  1. 長度：這一段有幾個叢集
  2. 起始 LCN：這一段從哪個叢集開始

而 NTFS 把這份清單編碼成非常緊湊的二進位格式——我們接下來就要學怎麼解碼。

10. Runlist 完整拆解教學

10.1 總體結構

Run 1: header length start_bytes...
Run 2: header length start_bytes...
Run 3: header length start_bytes...
00    ← 結束標記（header byte 的位置出現 00）

每一行（Run）的第一個 byte 叫做 header byte，它告訴你接下來的格式。

10.2 Header Byte 的解讀

Header byte 由兩個「半 byte」（nibble）組成：

例如 header byte = 0x21

左半 nibble = 2  →  Start 欄位佔 2 bytes
右半 nibble = 1  →  Length 欄位佔 1 byte

整筆 Run 的長度 = 1 (header) + 1 (length) + 2 (start) = 4 bytes
初學者最容易搞錯的地方：左半 nibble 是 Start 的 byte 數，右半 nibble 是 Length 的 byte 數。很多人會搞反！
Header左半 (Start)右半 (Length)總長度
212 bytes1 byte1+1+2 = 4 bytes
313 bytes1 byte1+1+3 = 5 bytes
222 bytes2 bytes1+2+2 = 5 bytes
111 byte1 byte1+1+1 = 3 bytes

10.3 實際解碼範例

範例：Run 1

Hex:  21 18 30 31

拆解：
21    → header: length 1 byte, start 2 bytes
18    → length = 0x18 = 24（叢集）
30 31 → start = 反轉為 0x3130 = 12,592（LCN）

結果：Run 1: LCN 12,592, 長度 24 叢集

範例：Run 2（注意！）

Hex:  22 14 00 78 EC

拆解：
22    → header: length 2 bytes, start 2 bytes
14 00 → length = 反轉為 0x0014 = 20（叢集）
78 EC → start = 反轉為 0xEC78

⚠️ 但 0xEC78 怎麼轉換成 -5,000？
我們在「10.6 負數」章節會詳細說明。

範例：Run 3

Hex:  21 0E 28 23

拆解：
21    → header: length 1 byte, start 2 bytes
0E    → length = 0x0E = 14（叢集）
28 23 → start = 反轉為 0x2328 = 9,000？？？

等一下，0x2328 = 9,000，但 Run 3 的 LCN 應該是 16,592 啊？
問題出在哪？

答案：Run 2 之後的 start 是「相對值」！不是絕對 LCN！
關鍵概念——必須徹底理解：

只有 Run 1 的 start 是 絕對 LCN。

Run 2 之後的 start 是 相對於前一個 Run 的 LCN 的偏移值。

正確計算方式：

Run 1 的 LCN = 12,592（絕對值）

Run 2 的相對偏移 = 0xEC78 → 反轉 → 0xEC78 → 負數 → -5,000
Run 2 的 LCN = 12,592 + (-5,000) = 7,592 ✓

Run 3 的相對偏移 = 0x2328 → 反轉 → 0x2328 = 9,000（正數）
Run 3 的 LCN = 7,592 + 9,000 = 16,592 ✓

10.4 補充：Little-Endian（小端序）

電腦在儲存多位元組的數值時，有兩種方式：

  • Big-Endian（大端序）：跟人類閱讀習慣一樣，高位元組在前。例如 30 31 = 0x3031 = 12,337
  • Little-Endian（小端序）：低位元組在前。30 31 要反轉為 31 30 再讀 = 0x3130 = 12,592
NTFS 使用 Little-Endian。所以看到 30 31 時，不要直接讀成 0x3031！要先反轉成 31 30，才得到正確的 0x3130。
原始 bytes正確反轉後十進位值
30 3131 30 → 0x313012,592
14 0000 14 → 0x001420（不是 5,120！）
78 ECEC 78 → 0xEC7860,536（但這是負數，見下節）

10.5 補充：Signed（帶符號）整數與負數

Runlist 中的相對偏移是 signed（帶符號） 的，也就是說它可以是正數或負數。正數表示「往前移動」，負數表示「往後移動」。

如何判斷正負

反轉完 bytes 之後，看最高位（最左邊的 hex digit）：

0x0000 ~ 0x7FFF  →  最高位 byte < 0x80  →  正數
0x8000 ~ 0xFFFF  →  最高位 byte ≥ 0x80  →  負數

如果是負數，怎麼轉成十進位？

三步驟：負數轉換

原始 bytes: 78 EC

步驟 1：反轉 bytes
78 EC → EC 78 → 0xEC78

步驟 2：檢查最高位
E ≥ 8 → 這是負數

步驟 3：減去 wrap value（0x10000 = 65,536）
0xEC78 - 0x10000 = 60,536 - 65,536 = -5,000
自我檢查：這個課程中的磁碟總共有 25,599 個叢集。如果你算出來的 LCN 大於 25,599，或者 LCN 變成負數（而且不是在 Run 2 之後），你一定搞錯了某個步驟——通常是忘記處理負號。

11. Runlist 實戰解碼——一步步跟著做

現在我們把所有知識串起來，實際解碼 record 61（manifest_0448.png）的 Runlist。

前置步驟：找到 $DATA 屬性

  1. 跳到 MFT record 61 的起始位置
  2. 搜尋 80 00 00 00（$DATA 簽名）
  3. 檢查 non-resident flag（第二個 byte）是 01
  4. 從 $DATA 開頭往後數 64 bytes（0x40），那就是 Runlist 的起點

解碼 Run 1

Hex: 21 18 30 31

header = 21  →  右 nibble = 1 (長度 1 byte), 左 nibble = 2 (起點 2 bytes)
length = 18  →  0x18 = 24 叢集
start  = 30 31 → 反轉 → 31 30 → 0x3130 = 12,592

✅ Run 1: LCN = 12,592, 長度 = 24 叢集
   Byte offset = 12,592 × 4,096 = 51,576,832
   結束位置 = 51,576,832 + (24 × 4,096) - 1 = 51,675,135

解碼 Run 2

Hex: 22 14 00 78 EC

header = 22  →  右 nibble = 2 (長度 2 bytes), 左 nibble = 2 (起點 2 bytes)
length = 14 00 → 反轉 → 00 14 → 0x0014 = 20 叢集
start  = 78 EC → 反轉 → EC 78

檢查符號：E ≥ 8 → 負數
0xEC78 - 0x10000 = -5,000

Run 2 的 LCN = Run 1 的 LCN + (-5,000) = 12,592 - 5,000 = 7,592

✅ Run 2: LCN = 7,592, 長度 = 20 叢集
   Byte offset = 7,592 × 4,096 = 31,096,832

解碼 Run 3

Hex: 21 0E 28 23

header = 21  →  右 nibble = 1, 左 nibble = 2
length = 0E  →  0x0E = 14 叢集
start  = 28 23 → 反轉 → 23 28 → 0x2328

檢查符號：2 < 8 → 正數 → 9,000

Run 3 的 LCN = Run 2 的 LCN + 9,000 = 7,592 + 9,000 = 16,592

✅ Run 3: LCN = 16,592, 長度 = 14 叢集
   Byte offset = 16,592 × 4,096 = 67,964,832

驗證總量

總叢集數 = 24 + 20 + 14 = 58 叢集
總分配空間 = 58 × 4,096 = 237,568 bytes
🎉 解碼完成！我們知道檔案的三段分別在 byte offset 51,576,832、31,096,832、67,964,832 開始。

12. 檔案大小陷阱：Allocated vs Logical Size

你可能以為「58 × 4,096 = 237,568 bytes 就是檔案大小了」。但事實上，檔案真正的長度比較小。

名詞意義範例
Allocated Size（分配大小） 檔案在磁碟上佔用的空間 = 叢集數 × cluster size 58 × 4,096 = 237,568 bytes
Logical / Real Size（邏輯大小） 檔案真正的資料長度 235,417 bytes

差的 2,151 bytes（237,568 - 235,417）是 slack（剩餘空間）——最後一個叢集中未被檔案使用的尾巴。這些 bytes 裡可能含有其他檔案的殘留資料，不是這個檔案的一部分。

非常重要：如果你不把尾巴砍掉就去算 hash，你的 hash 和老師的 hash 對不上。hash 比對的是「檔案真正的內容」，不是「檔案加上無關的 slack」。

在哪裡讀到 Logical Size？

在 $DATA 屬性標頭中，從屬性開頭算起 offset 0x30 處，有三個連續的 8-byte 欄位：

  • Allocated Size
  • Real (Logical) Size ← 我們要的
  • Initialized Size

13. 實際 Carve 檔案——把資料從磁碟挖出來

現在我們有了解碼後的 Run 資訊，可以開始動手了。整個過程只有 四個動詞：

Select（選取） → Copy（複製） → Concatenate（拼接） → Trim（修剪）

步驟 1：選取 Run 1

  1. 在十六進位編輯器中按 Ctrl+G，輸入 byte offset：51,576,832
  2. 標記為選取起點
  3. 再按 Ctrl+G，輸入結束 offset：51,576,832 + (24×4,096) - 1 = 51,675,135
  4. 標記為選取終點
  5. 複製到新檔案 → 命名為 run1.bin

步驟 2：選取 Run 2

  1. 跳到 offset：31,096,832
  2. 選取 20 × 4,096 = 81,920 bytes
  3. 複製為 run2.bin

步驟 3：選取 Run 3

  1. 跳到 offset：67,964,832
  2. 選取 14 × 4,096 = 57,344 bytes
  3. 複製為 run3.bin

步驟 4：拼接（按照 VCN 順序！）

Windows 命令列：
  copy /b run1.bin + run2.bin + run3.bin assembled.bin

或在 HxD 中直接將三個檔案依序複製貼上。
順序絕對不能錯！ 磁碟上的順序是 Run 2 → Run 1 → Run 3，但檔案內的順序是：先 Run 1 (VCN 0-23)、再 Run 2 (VCN 24-43)、最後 Run 3 (VCN 44-57)。拼接必須照 VCN 順序，而不是 LCN 順序。

步驟 5：修剪（Trim）

assembled.bin 的長度 = 237,568 bytes
但檔案的 Logical Size = 235,417 bytes

多出的 2,151 bytes 要砍掉。

在 HxD：Ctrl+E → 輸入起始位置 235,417 → 選擇到結尾 → 刪除

步驟 6：重新命名

將檔案重新命名為 manifest_0448.png

14. 三層驗證：簽名、打開、Hash

復原完檔案後，我們需要證明這個檔案是正確的、完整的、未被篡改的。

第一層：檢查簽名

用十六進位編輯器打開 recovered.png
檢查前 8 個 bytes 是否為：

89 50 4E 47 0D 0A 1A 0A

這是標準的 PNG 檔案簽名。
如果對了 → 代表 Run 1 的起始位置是正確的。

第二層：確認可以打開

直接雙擊檔案，看圖片檢視器能不能正常顯示。如果能看到圖片 → 大部分資料是正確的。

第三層：比對 Hash（最嚴格）

在 Windows 命令列：
  certutil -hashfile manifest_0448.png MD5

在 Linux：
  md5sum manifest_0448.png

你的 MD5 值和老師的 MD5 值必須完全一樣。
這代表檔案和原始檔案一模一樣——連一個 bit 都沒差。
為什麼 hash 很重要？在法庭上，你必須能證明「這個檔案就是我從嫌犯電腦中復原的檔案，而且我沒有動過它」。hash 就是最好的證據。

15. Carving（雕刻）是什麼？為什麼不夠？

Signature Carving 的原理

不靠任何檔案系統資訊，直接掃描整顆硬碟，尋找特定檔案類型的「簽名」：

檔案類型開頭簽名結尾簽名
PNG89 50 4E 4749 45 4E 44
JPEGFF D8 FFFF D9
PDF25 50 44 46 (%PDF)
ZIP / docx / xlsx50 4B (PK)

Carving 的致命弱點：碎片化

回頭看我們的檔案：Run 2（LCN 7,592）在磁碟上位於 Run 1（LCN 12,592）之前。如果 Carver 從 Run 1 的開頭開始讀，它會一路往下讀到 Run 2——但那是錯的！因為 Run 2 不在 Run 1 的後面，而是在 Run 1 的前面。

Carving 還缺少什麼？

透過 Runlist 復原透過 Carving 復原
知道檔名：manifest_0448.png無法知道檔名：f0001234.png
知道路徑：\MANIFESTS\（已刪除）沒有路徑
有建立、修改、刪除時間沒有時間戳記
知道來自 MFT record 61沒有記錄來源
精確長度：235,417 bytes長度由 Carver 猜測
同樣的 bytes，只有 Runlist 復原的結果能說出完整的故事——這是鑑識和一般資料救援的差別。

各種媒體的復原期望

媒體類型復原成功率原因
傳統硬碟 (HDD)✅ 良好資料會一直躺在那裡，直到被覆寫
USB 隨身碟 / SD 卡⚠️ 尚可控制器簡單，通常不支援 TRIM
現代 SSD（有 TRIM）❌ 差系統會在背景自動清除已刪除的資料
加密手機🚫 近乎零沒有密碼或金鑰就無法解密
在答應任何人「一定能救回檔案」之前，先搞清楚對方用的是什麼類型的儲存裝置！

16. 常見錯誤診斷

錯誤現象幾乎可以肯定是…怎麼辦？
算出來的 LCN 大於 25,599 忘了處理負號——把負數當正數加了 回頭檢查 Run 2 的相對偏移。它的最高位是不是 ≥ 8？
LCN 和 offset 看似正確，但拷貝出來的資料是亂碼 Nibble 搞反了——把 Length 的 byte 數和 Start 的 byte 數弄反了 記住：左 nibble = Start，右 nibble = Length
99% 的檔案正確，但最後一小段損壞 Run 順序錯了，或某個 Run 的 LCN 算錯 重新檢查 Run 2 的相對偏移是否為負，以及 Run 3 是從 Run 2 加過去的
檔案打得開，但 hash 不符 忘記 Trim——多了 slack bytes 回到 $DATA 標頭讀取 Logical Size，重新 trim
放輕鬆：錯誤的 carve 是正常的、可預期的、可診斷的。唯一的真失敗是放棄診斷。
