🛠️ ImHex 完整解題操作指南

使用 ImHex 十六進位編輯器，逐步完成 NTFS Runlist 資料復原的所有任務

📋 任務總覽

  1. 從 $Boot 讀取磁碟幾何（Cluster Size、$MFT Offset）
  2. 在 $MFT 中找到目標檔案的記錄與 Byte Offset
  3. 確認記錄為 DELETED 且 $DATA 為 NON-RESIDENT
  4. 解碼 Runlist：長度 · 相對偏移 · 絕對 LCN · Byte Offset
  5. Carve 資料、依 VCN 順序組合、Trim、計算 Hash

📁 使用檔案：HL-WS02.001（主示範）與 HL-WS03.001（團隊練習）

0. 開始之前 — ImHex 基本操作

快捷鍵功能用途
Ctrl+O開啟檔案載入 .001 磁碟映像檔
Ctrl+G跳到偏移（Goto）輸入十或十六進位 offset 直接跳位置

任務 1 — 從 $Boot 讀取磁碟幾何

STEP 1 開啟檔案：File → Open → 選擇 HL-WS02.001

打開後，游標預設在 offset 0x00000000，這就是 $Boot 的第一個 sector（前 512 bytes）。

1.1 讀取 Bytes per Sector

📍 操作步驟
  1. 按 Ctrl+G，輸入 0x0B（$Boot 內的偏移位置）
  2. 看到兩個 bytes：00 02
  3. ImHex 的 Data Inspector 右側會自動顯示：uint16 = 512
理論實作結果
Bytes per Sector 位於 offset 0x0B，2 bytes，Little-Endian 00 02 → 反轉讀取 → 0x0200 → 512
📟 ImHex 畫面模擬（offset 0x0B）
0000000B 00 02 08 00 00 00 00 00 00 F8 00 00 00 00 00 00
↑↑
bytes per sector = 0x0200 = 512

1.2 讀取 Sectors per Cluster

📍 操作步驟
  1. 按 Ctrl+G，輸入 0x0D
  2. 看到一個 byte：08
  3. Cluster Size = 512 × 8 = 4,096 bytes

1.3 讀取 $MFT 起始叢集

📍 操作步驟
  1. 按 Ctrl+G，輸入 0x30
  2. 看到 8 個 bytes：04 00 00 00 00 00 00 00
  3. Data Inspector 顯示為 uint64 = 4（$MFT 在 Cluster 4）
  4. $MFT Byte Offset = 4 × 4,096 = 16,384

1.4 驗證 $MFT 位置

📍 操作步驟
  1. 按 Ctrl+G，輸入 16384（或 0x4000）
  2. 檢查這 4 個 bytes：46 49 4C 45 = ASCII FILE ✓
  3. 第 5 個 byte 為 30（即 0），合起來就是 FILE0
任務 1 結果
Bytes per Sector = 512
Sectors per Cluster = 8
Cluster Size = 4,096 bytes
$MFT Start Cluster = 4
$MFT Byte Offset = 16,384
這組數字對 HL-WS02.001 和 HL-WS03.001 都適用（兩顆都是同一批建立的 NTFS 磁碟）。如果你在不一樣的映像檔上操作，請重新讀取一次！

任務 2 — 在 $MFT 中找到目標記錄

目標：找到 manifest_0448.png（HL-WS02.001 上的已刪除貨運艙單）。

方法 A：直接跳到已知 Record Number

根據課程提示，manifest_0448.png 是 Record 61。

📍 操作步驟
  1. 每筆 MFT 記錄固定 1,024 bytes
  2. Record 61 的偏移 = $MFT offset + (61 × 1,024)
  3. = 16,384 + 62,464 = 78,848（即 0x13400）
  4. 按 Ctrl+G，輸入 0x13400
📟 ImHex — Record 61 開頭
00013400 46 49 4C 45 30 00 03 00 00 00 00 00 00 00 00 00 │ FILE0........... 00013410 03 00 01 00 38 00 00 00 70 01 00 00 00 04 00 00 │ ....8...p.......

確認看到 FILE0 簽名，表示這確實是一筆 MFT 記錄。

方法 B：搜尋檔名（如果不知道 Record Number）

📍 操作步驟
  1. 按 Ctrl+F，切換到 ASCII 搜尋模式
  2. 但檔名在 NTFS 中是 Unicode（UTF-16LE）儲存的，不能直接搜尋 ASCII
  3. 改成用 Hex 搜尋： 
    6d 00 61 00 6e 00 69 00 66 00 65 00 73 00 74 00 5f 00 30 00 34 00 34 00 38 00
    （這是 manifest_0448 的 UTF-16LE 編碼）
  4. 按 F3 尋找下一個直到找到目標
  5. 找到後，該檔名所在的 MFT 記錄開頭必定在前方不遠處且以 FILE0 開始
  6. 或者直接檢查「該檔名所在的記錄」。找到後檢查記錄偏移 0x2C 處的 4 bytes → 就是 Record Number
任務 2 結果
manifest_0448.png → MFT Record 61
Record Byte Offset = 0x13400 (78,848)
如果之後你在 HL-WS03.001 上操作團隊任務：
Team A：manifest_0511.png → Record 46（offset 0xF800 = 63,488）
Team B：manifest_0512.png → Record 61（offset 0x13400 = 78,848）

任務 3 — 確認 DELETED 與 NON-RESIDENT

3.1 檢查 Allocation Status（是否為已刪除）

📍 操作步驟
  1. 目前在 Record 61 開頭（0x13400）
  2. 記錄內偏移 0x16 處 = 檔案偏移 0x13416
  3. 按 Ctrl+G，輸入 0x13416
  4. 看到 2 個 bytes：00 00
📟 Record 61, offset 0x16
00013414 38 00 00 00 70 01 00 00 00 04 00 00 │ 8...p....... ↑ ↑ attr flags = 0x0000 → DELETED FILE offset
Flags 值意義
00 00已刪除檔案 ✅ ← 我們要的
01 00正常檔案
02 00已刪除目錄
03 00正常目錄

3.2 找到 $DATA 屬性

📍 操作步驟
  1. 按 Ctrl+F，切換到 Hex 搜尋模式
  2. 搜尋 80 00 00 00（$DATA 屬性的簽名）
  3. 游標會跳到 Record 61 範圍內的第一個 80 00 00 00
  4. 確定位於 Record 61 內（offset 0x13518）
📟 $DATA 屬性開頭（offset 0x13518）
00013518 80 00 00 00 50 00 00 00 01 00 00 00 00 00 02 00 │ ....P........... 00013528 00 00 00 00 00 00 00 00 39 00 00 00 00 00 00 00 │ ........9.......

欄位解析：

Attr 內偏移值意義
0x00 (type)80 00 00 00這是 $DATA 屬性
0x04 (length)50 00 00 00屬性總長度 = 0x50 = 80 bytes
0x08 (resident flag)01NON-RESIDENT ✅ → 內容不在記錄內，在 Runlist 裡
任務 3 結果
✅ Allocation Status 在 offset 0x13416 = 00 00 → DELETED FILE
✅ $DATA Non-resident flag 在 offset 0x13520 = 01 → NON-RESIDENT
→ 檔案已刪除，內容在 Runlist 中，可以開始解碼！

任務 4 — 解碼 Runlist

這是整份課程的核心。我們要從 $DATA 屬性中讀出 Runlist，解碼出三個 Run 的長度、LCN、Byte Offset。

4.1 找到 Runlist 的起始位置

📍 規則 Runlist 從 $DATA 屬性開頭往後數 0x40（64）bytes 開始。
$DATA 在 0x13518，所以 Runlist 在 0x13518 + 0x40 = 0x13558。
📟 Runlist 原始資料（offset 0x13558）
00013558 21 18 30 31 22 14 00 78 EC 21 0E 28 23 00

顏色標示：■ Header · ■ Length · ■ Start (相對 LCN) · ■ End

4.2 解碼 Run 1

步驟Hex計算結果
讀取 Header 21 右 nibble = 1 → Length 佔 1 byte
左 nibble = 2 → Start 佔 2 bytes
整筆 = 1+1+2 = 4 bytes		 ✓
讀取 Length 18 1 byte，直接讀 → 0x18 = 24 24 clusters
讀取 Start 30 31 Little-Endian → 反轉為 31 30 → 0x3130 LCN = 12,592
Byte Offset 12,592 × 4,096 = 51,576,832 ✅
Run 1：LCN 12,592 · 長度 24 叢集 · Byte Offset 51,576,832

4.3 解碼 Run 2（關鍵：含負數運算）

步驟Hex計算結果
讀取 Header 22 右 nibble = 2 → Length 佔 2 bytes
左 nibble = 2 → Start 佔 2 bytes
整筆 = 1+2+2 = 5 bytes		 ✓
讀取 Length 14 00 2 bytes LE → 反轉為 00 14 → 0x0014 20 clusters
讀取 Start（相對） 78 EC 反轉為 EC 78 → 0xEC78
E ≥ 8 → 負數
0xEC78 - 0x10000 = -5,000		 相對 = -5,000
計算絕對 LCN Run 1 的 LCN + (-5,000) = 12,592 - 5,000 LCN = 7,592
Byte Offset 7,592 × 4,096 = 31,096,832 ✅
🚨 Run 2 的 Start 是「相對於 Run 1 的 LCN」，而且是「帶符號整數」！
看到 78 EC 先反轉為 EC 78，最高位 E ≥ 8 → 負數！
0xEC78 - 0x10000 = -5,000 → Run 2 在 Run 1 的「左邊」5,000 個叢集。
Run 2：LCN 7,592 · 長度 20 叢集 · Byte Offset 31,096,832

4.4 解碼 Run 3

步驟Hex計算結果
讀取 Header 21 Length 1 byte, Start 2 bytes → 4 bytes ✓
讀取 Length 0E 0x0E 14 clusters
讀取 Start（相對） 28 23 反轉為 23 28 → 0x2328
2 < 8 → 正數
0x2328 = 9,000		 相對 = +9,000
計算絕對 LCN Run 2 的 LCN + 9,000 = 7,592 + 9,000 LCN = 16,592
Byte Offset 16,592 × 4,096 = 67,964,832 ✅
Run 3：LCN 16,592 · 長度 14 叢集 · Byte Offset 67,964,832

4.5 計算檔案大小

📍 從 $DATA Header 讀取 Logical Size
  1. $DATA 開頭在 0x13518
  2. 屬性內偏移 0x30 = 檔案偏移 0x13548
  3. 看到 8 bytes：99 97 03 00 00 00 00 00
  4. 反轉為 00 00 00 00 00 03 97 99 → 0x00039799
  5. Logical Size = 235,417

Allocated Size(24+20+14) × 4,096237,568 bytes

Slack237,568 - 235,4172,151 bytes（最後要砍掉）

任務 5 — Carve、組合、Trim、Hash

5.1 選取並匯出 Run 1

📍 操作步驟
  1. 按 Ctrl+G，輸入 51576832（Run 1 的起始偏移）
  2. 按 Ctrl+E（選取範圍）
  3. 輸入長度 98304（24 × 4,096）
  4. 對選取區按右鍵 → Export → 命名為 run1.bin

5.2 選取並匯出 Run 2

📍 操作步驟
  1. 按 Ctrl+G，輸入 31096832
  2. 按 Ctrl+E，輸入長度 81920（20 × 4,096）
  3. 匯出為 run2.bin

5.3 選取並匯出 Run 3

📍 操作步驟
  1. 按 Ctrl+G，輸入 67960832
  2. 按 Ctrl+E，輸入長度 57344（14 × 4,096）
  3. 匯出為 run3.bin
再次確認三條資料的起點和長度：
Run 1: offset 51,576,832, 長度 98,304
Run 2: offset 31,096,832, 長度 81,920
Run 3: offset 67,960,832, 長度 57,344
注意：Run 2 的 offset 比 Run 1 小 -> 它在磁碟上位於 Run 1 之前

5.4 按照 VCN 順序拼接

🚨 順序絕對不能錯！
磁碟上的順序是 Run 2 → Run 1 → Run 3，但檔案的 VCN 順序是 Run 1 → Run 2 → Run 3。
我們要按照 VCN 順序（0→23, 24→43, 44→57）拼接。
📍 拼接方法

方法 1：命令列（建議）

copy /b run1.bin + run2.bin + run3.bin assembled.bin

方法 2：手動拼接（在 ImHex 中）

  1. 開啟一個新檔案（File → New）
  2. 依序開啟 run1.bin、run2.bin、run3.bin
  3. 全選 run1.bin 的內容，複製到新檔案
  4. 全選 run2.bin 的內容，接續貼上
  5. 全選 run3.bin 的內容，接續貼上

5.5 Trim——切除 Slack

📍 操作步驟
  1. assembled.bin 目前大小 = 237,568 bytes
  2. 但檔案的 Logical Size = 235,417 bytes
  3. 多出的 2,151 bytes 是 slack，必須砍掉
  4. 在 ImHex 中：
    • 按 Ctrl+G，輸入 235417
    • 從這裡選取到結尾（按 Ctrl+Shift+End）
    • 按 Del 刪除
  5. 或使用 HxD 風格的 Ctrl+E → 起始 235417 → 長度到結尾 → 刪除
為什麼要 Trim？
如果不砍 slack，最後計算的 MD5 會和老師的不同。Hash 比對的是「檔案真正的內容（235,417 bytes）」，不是「檔案加垃圾（237,568 bytes）」。

5.6 重新命名

將 trimmed 檔案重新命名為 manifest_0448.png

5.7 三層驗證

🔍 第 1 層：檢查簽名
  1. 在 ImHex 中開啟 manifest_0448.png
  2. 前 8 個 bytes 必須是：
    3. 89 50 4E 47 0D 0A 1A 0A
  3. 這是標準的 PNG 檔案簽名 → 表示 Run 1 的起點正確
🔍 第 2 層：能否打開
  1. 直接雙擊檔案
  2. 若 PNG 檢視器能正常顯示圖片 → 大部分資料正確
🔍 第 3 層：計算 MD5（最嚴格）

在終端機中：

# Linux
md5sum manifest_0448.png

# Windows
certutil -hashfile manifest_0448.png MD5

比對結果是否與老師提供的 MD5 一致。若一致 → 檔案完全正確。

❌ 常見錯誤速查表

症狀原因解法
LCN 算出來超過 25,599 Run 2 的負號沒處理 Run 2 的 Start 反轉後檢查最高位是否 ≥ 8。如果是，要減去 65,536。
Runlist Header 讀錯，整筆資料亂掉 Left/Right Nibble 搞反 左 nibble = Start 的 byte 數，右 nibble = Length 的 byte 數。順序是 Length bytes 在前，Start bytes 在後。
最後拼接的檔案大部分正確但尾巴壞了 Run 的順序錯誤 確認拼接順序是 VCN 順序（Run 1 → Run 2 → Run 3），不是 LCN 順序（Run 2 → Run 1 → Run 3）
圖檔打得開但 MD5 不符 忘記 Trim 回到 $DATA header 讀取 Logical Size，將檔案裁切到正確大小再重新計算 MD5。
Goto 某個 offset 但看到的資料不對 Cluster Size 算錯 回去重新確認 $Boot 的 bytes per sector 和 sectors per cluster。Cluster Size = 512 × 8 = 4,096。

🎯 結語

你現在已經學會了：

  1. 用 ImHex 開啟裸磁碟映像檔並導航
  2. 從 $Boot Sector 讀取磁碟幾何參數
  3. 在 $MFT 中根據記錄編號或檔名找到目標
  4. 讀取 Allocation Status 判斷是否已刪除
  5. 找到 $DATA 屬性並確認 Resident / Non-Resident
  6. 從 Runlist 解碼出每個 Run 的長度、相對偏移、絕對 LCN 和 Byte Offset
  7. 用 ImHex 選取、匯出每個 Run 的資料
  8. 按照 VCN 順序拼接、Trim、Hash 驗證
